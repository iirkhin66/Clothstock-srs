## Результаты выполненных заданий

### Задача 1 — Концепция программного продукта

Разработана концепция системы **ClothStock** — веб-приложения для учёта товаров небольшого магазина одежды.

- Описана проблема: менеджеры ведут учёт остатков вручную в Excel, что приводит к ошибкам и потере продаж из-за незамеченного дефицита.
- Определены заинтересованные лица и назначение системы.
- Построена контекстная диаграмма: 3 роли пользователей + 3 внешних сервиса.
- Проведён сравнительный анализ 3 конкурентов одного сегмента (XS–S): **Shopify POS**, **ЕКАМ**, **МойСклад**. Составлена таблица с приоритетами e/u/d.
- Сформулировано описание продукта по шаблону Мура (Crossing the Chasm).

### Задача 2 — Моделирование пользовательских требований

Выделены 3 роли пользователей методом опорных точек зрения:

| Роль | Категория | Потребности |
|------|-----------|-------------|
| Кассир | U (обычный) | Поиск товара, просмотр остатка |
| Менеджер | Р (продвинутый) | Управление каталогом, остатками, отчёты |
| Администратор | XS (корпоративный) | Управление учётными записями сотрудников |

Составлены 4 варианта использования (Use Case) в формате: актор, предусловие, основной поток, альтернативные потоки, постусловие:
- UC-01: Добавить товарную позицию
- UC-02: Найти товар
- UC-03: Скорректировать остаток
- UC-04: Управлять учётными записями сотрудников

### Задача 3 — Систематизация требований

На основе сценариев использования составлен структурированный список требований с применением **комбинированного метода**:

**Матрица классификации** (4 категории × 3 роли, 12 функциональных требований):

| Категория | Кассир | Менеджер | Администратор |
|-----------|--------|----------|---------------|
| Управление товарами | FR-01 | FR-02, FR-03, FR-04 | — |
| Управление остатками | FR-05 | FR-06, FR-07 | — |
| Уведомления и отчёты | — | FR-08, FR-09 | — |
| Управление пользователями | — | — | FR-10, FR-11, FR-12 |

**Диаграмма Венна**: выявлены 2 пересекающихся требования (общих для Кассира и Менеджера):
- FR-01 — Поиск товара
- FR-05 — Просмотр остатка

Все требования сформулированы атомарно, однозначно и проверяемо по правилу «один глагол» («Менеджер **может** добавить...», «Система **отправляет** уведомление, когда...»). Указаны приоритеты MoSCoW (e/u/d).

### Задача 4 — Спецификация требований (SRS)

Составлена итоговая Спецификация требований к ПО по стандарту **IEEE 830 / ISO 29148**, интегрирующая результаты задач 1–3.

Структура документа:
1. Введение (цель, область применения, определения)
2. Общее описание (концепция, контекстная диаграмма, анализ конкурентов, роли, ограничения)
3. Функциональные требования (Use Cases + матрица + диаграмма Венна + перечень FR)
4. Нефункциональные требования (производительность, надёжность, безопасность)
5. Внешние интерфейсы (UI, API, БД, сервисы)
6. Критерии приёмки
